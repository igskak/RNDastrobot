План реализации импорта карт в Steliara

Дата: 2026-09-20. Статус: исторический план первой версии (ZET и AAF реализованы). Дополнительные форматы описаны в [chart-import-formats.md](../chart-import-formats.md).

**1. Задача и границы первой версии**

Дать астрологу возможность самостоятельно перенести исходные данные карт из другой программы: загрузить файл, проверить записи, выбрать размещение и сохранить карты с понятным отчётом.

- Постоянный вход: «Настройки → Импорт карт». Отдельная вкладка настроек, без новой постоянной кнопки в библиотеке.
- Дополнительный вход: предложение импорта в начале существующего онбординга после регистрации/первого авторизованного входа. Можно пропустить и вернуться через настройки.
- Форматы первой версии: ZET `.zbs` и AAF (`.aaf`, а также `.txt` с содержимым AAF).
- Оба варианта размещения доступны пользователю: отдельные карты либо все выбранные карты в одном существующем/новом профиле.
- Общие теги можно назначить при любом варианте размещения. Они добавляются самим новым картам, а не меняют теги существующего профиля.
- Переносятся исходные данные и комментарии. Расчёты выполняет Steliara. Не обещать перенос интерпретаций, оформления, всех настроек и производных карт исходной программы.
- Solar Fire / Astro Gold `.SFcht` — отдельный следующий этап после изучения образцов. В первой версии не отображать эти форматы как поддерживаемые.
- Не включать универсальную синхронизацию, массовое обновление существующих карт, автоматическое объединение людей, отмену всего импорта или обязательную новую инфраструктуру очередей.

**2. Обязательные продуктовые решения и тексты**

В интерфейсе использовать «профиль», «человек», «карта», «библиотека». Термин «клиент» не использовать. Старые технические имена `clients.html`, `Person`, `person_id` переименовывать не требуется.

Онбординг:

> Уже есть карты в другой программе?
>
> Перенесите их сюда, чтобы не вводить всё заново.
>
> Импортировать карты · Пропустить
>
> Сделать это позже можно в разделе «Настройки → Импорт карт».

Вариант «Отдельные карты»:

> Каждая запись из файла появится отдельной картой в вашей библиотеке. Подходит, если в файле разные люди или события. Вы можете добавить один или несколько тегов (меток для поиска карт по теме), например «Работа», «Отношения» или «Обучение», чтобы потом легко находить нужные карты.

Вариант «Все карты в одном профиле»:

> Профиль объединяет несколько карт в одном месте — например, карту рождения человека и карты важных событий его жизни. Выберите существующий профиль или создайте новый.

Поля: «Выбрать профиль» / «Создать новый профиль», «Название профиля», «Теги (метки)». Использовать существующие подсказки тегов библиотеки, разрешить несколько новых меток. Не создавать метку по имени файла молча: можно предложить её как необязательный вариант.

Оба варианта размещения показывать одновременно как radio-карточки с пояснениями. Первоначально выбран вариант «Отдельные карты». При втором варианте раскрывать выбор профиля. Название файла без расширения можно предложить для нового профиля, оставив редактируемым. Никаких профилей или карт до подтверждения не создавать.

Итог перед подтверждением, например:

> Будет добавлено 27 карт в профиль «!текущий».

Либо:

> Будет добавлено 27 отдельных карт в библиотеку. Теги: «Обучение».

Показывать отдельно число пропущенных записей и предупреждений. Кнопка: «Импортировать N карт»; при N = 0 недоступна.

Подсказка «Смещение UTC»:

> Это разница между местным временем и общим мировым временем. Например, UTC+3 означает: когда по мировому времени 9:00, в этом месте — 12:00.
>
> Для карты важно значение именно на дату события: раньше часы могли переводить по другим правилам. При импорте мы берём это значение из исходного файла.

В предпросмотре основной акцент на местных дате, времени и месте. Смещение показывать вторично, включая секунды, если они есть. Подсказка доступна по нажатию, с клавиатуры и при наведении; не ограничиваться HTML `title`.

**3. Сценарий и состояния интерфейса**

Один мастер внутри вкладки настроек, открываемый также из онбординга. Три шага: «Файл → Проверка → Сохранение». После подтверждения — прогресс и итог.

1. Файл: обычная кнопка выбора и drag-and-drop; один файл за раз. Автоопределение по расширению и структуре. Ссылка «Как выгрузить карты?» с короткими проверенными инструкциями для поддерживаемых источников. Несовпадение расширения/содержимого объяснять, не угадывать бинарные форматы.
2. Проверка: строки с названием, датой, местным временем, смещением, местом и статусом. Для больших файлов — пагинация, например 50 строк. Полные координаты, комментарии и объяснение проблемы раскрываются у строки. Статусы: «Готово», «Нужно проверить», «Не удалось прочитать», «Возможный повтор», «Уже импортирована».
3. Выбор строк: валидные новые записи выбраны, ошибки недоступны, возможные повторы первоначально не выбраны, но пользователь может включить их явно. Предупреждения, меняющие результат расчёта, требуют осознанного подтверждения. Разрешить импорт исправных строк, ясно показывая пропуски. Полный редактор повреждённых записей отложить: предложить исправить исходный файл и загрузить снова.
4. Сохранение: выбрать размещение, профиль и общие теги; показать применяемые систему домов, зодиак и аянамшу, когда она нужна. Использовать существующие настройки аккаунта и элементы выбора. Эти значения относятся к импорту и не меняют настройки аккаунта.
5. Выполнение: «Сохранено 8 из 27»; кнопка «Приостановить» завершает текущую запись и не начинает следующую. При потере сети сверяться с серверным состоянием. Уже сохранённые карты остаются; продолжение не создаёт повторов.
6. Итог: добавлено / пропущено / ошибки; ссылки на библиотеку либо выбранный профиль. Отчёт по ошибкам доступен на экране и для скачивания в безопасном текстовом формате. Не обещать выполнение в фоне после закрытия вкладки для первой версии.

Определить loading/empty/error/success, состояние неподдерживаемого формата и превышения лимита файла. Не заменять полезное состояние общим «Что-то пошло не так». После ошибки сохранять выбор пользователя. Ошибки строк показывать рядом со строками, а не только всплывающим уведомлением.

Стартовые технические ограничения: 5 MiB на файл, 2000 записей, 64 KiB на исходную запись; константы на сервере, возвращаемые UI. Проверять размер потоково до декодирования. Эти ограничения — предложение реализации, их можно уменьшить по результатам измерений, явно отражая изменение в UI и тестах.

**5. Нормализация данных и адаптеры форматов**

Новые модули (точные имена можно согласовать со стилем актуального дерева):

- `app/models/chart_import.py` — схемы нормализованной записи, предупреждений, preview/confirm/result.
- `app/services/chart_import/parsers/zet.py`, `aaf.py`, `__init__.py` — чистые парсеры без сети, БД и вычисления натальной карты.
- `app/services/chart_import/service.py` — предпросмотр, сверка, выбор, расчёт и сохранение.
- `app/api/routes/chart_imports.py` — тонкий HTTP-слой.

Общий объект записи: стабильный source record index и строки источника; title / имена при наличии; исходные local date/time; offset_seconds и каноническая timezone; исходное место; latitude/longitude; comments; поддерживаемый chart_kind; source calendar; вычисленный UTC; опциональный исходный JD; warnings/errors с кодами и аргументами; fingerprint. Отсутствие значения не заменять вымышленным значением. Ошибку одной строки изолировать от остальных.

ZET:

- Поддержать UTF-8/BOM и Windows-1251 с детерминированным выбором и строгим декодированием; не использовать `errors=ignore/replace`. Неоднозначную кодировку показать в preview и дать переключить, если название выглядит неверно.
- Проверенный пример — текст с `;`, первые поля: название, дата `DD.MM.YYYY`, местное время `HH:MM[:SS]`, смещение `±H[:MM[:SS]]`, место, широта, долгота. Координаты образца — `DDnMM`, `DDeMM` и соответствующие s/w. Проверить дополнительные поля/экранирование по документации и обезличенным fixtures; не терять комментарий при дополнительных разделителях.
- Пустые строки не являются записями. Поддержать CRLF и LF, сохранить номера исходных строк.
- Не переносить эвристическое определение типа карты по словам в названии из разового скрипта. Использовать документированный тип источника; если его нет — `other` с понятным пояснением, название не менять.
- Опорный локальный файл: `/Users/ihorskakovskyi/Downloads/Telegram Desktop/!Текущая.zbs` (27 записей). Разовый скрипт `/private/tmp/zet_orlova_import.py` можно прочитать как исторический образец, если он ещё существует. Не запускать его и не копировать целиком: там конкретный аккаунт, обход ограничения времени и изменение глобального списка планет, непригодные для общего импорта.
- Реальный файл и персональные данные не добавлять в Git. Для тестов создать синтетические записи с теми же граничными условиями.

AAF:

- Начать с явно ограниченного профиля совместимости: исходные данные `#A93`, расчётные данные `#B93`, комментарии `#COM`; сохранять provenance из `#SRC`/`#VIA`, если есть. Не реализовывать импорт готовых положений планет вместо собственных расчётов.
- Разбирать целые записи с несколькими блоками; новая `#A93` начинает новую запись. Не считать каждую текстовую строку отдельной картой.
- Обязательно сверить по спецификации обозначения широты/долготы и знаков, календарь, источник UTC/JD и применение летнего времени. Проверять итоговый момент по независимым fixtures; не трактовать стандартное смещение как итоговое без учёта поля типа времени.

**6. Время, география и расчёт — инварианты**

- `UTC = local datetime − offset_seconds`; изменение даты при переходе через полночь обязательно учитывать.
- Хранить исходные местные дату, время и место в основных полях карты. Для явного смещения использовать существующий resolver и каноническую запись `UTC±HH:MM[:SS]`. Не округлять смещения/время до минут или часов.
- Явное историческое смещение из файла имеет приоритет над современным часовым поясом города. Не заменять его IANA-зоной, полученной геокодингом.
- При наличии координат использовать их, не искать город заново; исходное название места сохранять. Если координат или однозначного времени недостаточно, в первой версии отклонить строку с пояснением.
- После записи и повторного чтения исходный UTC должен совпадать до секунды. Для хранимого JD учесть реальную точность `Numeric(15,6)` и проверять допуск, а не требовать побитового совпадения float.
- Систему домов / зодиак / аянамшу брать из явно показанной конфигурации импорта, основанной на настройках аккаунта; не зашивать Placidus в парсер. Открыто пояснить: «Данные будут перенесены, а карты рассчитаны с выбранными здесь настройками».
- Переиспользовать `NatalChartService` и общий persistence; при необходимости выделить публичную операцию сохранения рассчитанной карты, не дублировать планеты/дома/аспекты в импортере. Запись карты и всех вычисленных таблиц должна быть атомарной.
- Для исторических дат в проекте известна ограниченная доступность эфемерид Прозерпины. Нельзя копировать временную подмену глобального `PLANETS` из разового скрипта. Нужна безопасная обработка отсутствующего необязательного объекта на уровне одного расчёта, согласованная с чтением/пересчётом карты и с предупреждением в preview и результате. Если это ещё не поддерживается, запись должна дать явную ошибку, а не фиктивные координаты или «успешный» полный расчёт. Полная совместимость с опорными 27 записями требует закрыть этот пункт до приёмки ZET.

**7. Серверное сохранение, повторы и возобновление**

Предложение для первой версии: последовательные короткие запросы на сохранение одной записи, с состоянием импорта в БД. Это позволяет показывать реальный прогресс и продолжать после обрыва без новой очереди задач. Не запускать весь файл одним длинным HTTP-запросом и не считать FastAPI BackgroundTasks надёжной очередью.

Добавить новой нумерованной миграцией две сущности:

- `ChartImportBatch`: owner, format, parser_version, file digest, original filename, status, frozen configuration, created/updated/expires timestamps, destination profile reference.
- `ChartImportItem`: batch, source index, normalized payload, fingerprint, issues, selection/status, resulting chart_id. Уникальность `(batch_id, source_index)`, индексы owner/fingerprint через модель хранения. Одна запись импорта должна атомарно ссылаться максимум на одну созданную карту.

Предлагаемые API под `/api/v1/chart-imports`:

| Запрос | Назначение |
|---|---|
| `GET /` | Недавние собственные импорты с кратким статусом и доступным действием «Продолжить»; без исходных строк и лишних персональных данных |
| `POST /preview` multipart | Ограничить/проверить файл, разобрать, сверить повторы, сохранить временный batch; вернуть id, summary, первую страницу. Карт/профилей не создавать |
| `GET /{id}` | Состояние, настройки, счётчики и продолжение после перезагрузки |
| `GET /{id}/items` | Страницы предпросмотра/результатов с фильтром статуса |
| `POST /{id}/confirm` | Зафиксировать выбранные source item ids, размещение, теги, настройки и признанные предупреждения; проверить владельца, готовность и квоту |
| `POST /{id}/items/{item_id}/commit` | Идемпотентно сохранить конкретную выбранную запись; повтор запроса возвращает ту же карту |

`confirm` тоже идемпотентен: тот же payload возвращает текущее состояние, изменённый после начала импорта — conflict. Новую конфигурацию создавать новым preview, не менять расчёт у уже записанных строк. Summary/status обновляются сервером; статус completed только после терминального результата всех выбранных строк. Повторить неуспешную строку можно отдельным явным действием после устранения временной ошибки; импортированная строка неизменяема.

Frontend вызывает commit последовательно. При неизвестном результате сетевого запроса запрашивает серверный статус и повторяет тот же item_id. В настройках показывать недавние незавершённые импорты, чтобы продолжение было доступно после закрытия вкладки и на другом устройстве. Сохранять в URL/локальном состоянии только id batch, а не исходные персональные данные. Deep link назад из онбординга должен быть локальным и проверенным.

Транзакции:

- Перед каждым сохранением повторно проверять writable/effective plan и реальную квоту. На confirm проверять весь выбранный объём; при нехватке не запускать произвольную часть без изменения выбора пользователем.
- Использовать блокировку batch/item для двух вкладок и общую защиту квоты аккаунта от конкурентного создания. Если обычное создание карт её не имеет, выделить небольшой общий guard и применить в обоих путях; импорт не должен обходить лимит гонкой.
- Карта + её вычисленные данные + связь с профилем + успешный receipt импортируемой строки фиксируются одной транзакцией. Проверить всю цепочку на внутренние commit, не предполагать атомарность по названию сервиса.
- При ошибке откатить только текущую карту и её побочные записи; сохранить диагностический код строки отдельно после rollback. Ранее сохранённые строки остаются.
- Новый общий профиль создавать в транзакции с первой успешной картой и закреплять в batch; не оставлять пустой профиль, если не сохранилось ничего. Остальные записи используют тот же профиль. Не изменять чужой/существующий профиль и его основную карту без необходимости.

Повторы — два разных случая:

- Повтор HTTP-запроса/возобновление batch: строгая идемпотентность, ноль новых копий.
- Повторная загрузка или похожая карта в библиотеке: receipt по owner + file digest + source record и проверка живой карты; дополнительно fingerprint по нормализованным исходным данным (включая имя/название, UTC до секунды, координаты и вид карты). Сравнение только по имени или дате запрещено. Совпадения внутри файла также показывать. Изменённый файл не должен обходить поиск возможных повторов.

Точное receipt-совпадение показывать как «Уже импортирована» и пропускать. Если связанная карта удалена или её существенные поля изменены, не скрывать запись навсегда: сверить фактическую карту и показать соответствующее состояние. Для похожих записей без точного receipt оставить явное «Импортировать всё равно»; существующие карты не перезаписывать и их теги не менять. Если ранее импортированная карта с теми же данными отличается только методом расчёта, считать её возможным повтором и объяснить различие.

Временные normalized payload/raw excerpts хранить до 24 часов, показывать срок пользователю; после истечения preview/возобновление требуют повторной загрузки. Очистку реализовать существующим механизмом задач либо ограниченным удалением истёкших данных при обращении к импорту. Для сохранённых карт оставить компактный receipt: источник, digest/index, parser version, fingerprint и chart_id, без полного файла. Комментарии сохраняются в карте. Логи/аналитика не содержат имён, дат рождения, исходных строк и содержимого файла. UI выводит значения как текст, не как HTML.

**10. Проверки и критерии готовности**

Парсеры:

- 27 синтетических ZET-записей, пустая строка, cp1251, UTF-8 BOM, LF/CRLF; комментарии и разделители; плохая строка не ломает весь файл.
- Положительные/отрицательные смещения, `+00:00`, `+05:30`, `+05:45`, `+00:52:08`, `−06:53:20`, `−00:14:28`; секунды во времени; переход UTC через сутки/год. Для файлов использовать документированные ASCII-знаки, UI может отображать типографский минус.
- Одинаковое название/дата/место с временем 16:00 и 16:10 — две разные карты.
- Неверные координаты, невозможная дата, отсутствующее время, неизвестная кодировка, не-AAF `.txt`, бинарный `.SFcht`, превышение лимитов — понятные ошибки.
- AAF: несколько блоков/записей, комментарии, часовые знаки, летнее время, JD с учётом точности, неизвестные значения, неподдерживаемый календарь/вид карты без ложного успеха.

API/БД:

- Preview не создаёт `User` или `Person`.
- Отдельный режим сохраняет `person_id=NULL` и не создаёт профили косвенно. Групповой режим создаёт ровно один новый профиль либо использует выбранный свой.
- Общие теги находятся на каждой новой карте и работают в существующем фильтре библиотеки.
- Повторный confirm/commit, двойной клик, два окна, обрыв после успешного commit и перезапуск процесса не создают дубликаты.
- Чужие batch/item/person/chart недоступны. Owner берётся исключительно из auth; нельзя подменить его в payload.
- Изменение плана между preview и commit, недостаток квоты и конкурентное создание корректно обработаны; не обходят ограничения.
- Искусственный сбой после записи части вычисленных таблиц полностью откатывает текущую карту, успешные прежние строки остаются.
- Повторное чтение сохранённой карты сохраняет исходные местные поля/координаты и UTC до секунды; последующее редактирование без изменения времени не сдвигает момент расчёта.
- Исторические записи не содержат выдуманных объектов и не меняют глобальную конфигурацию других запросов. Предупреждение об отсутствующем объекте согласовано с просмотром и пересчётом.
- Реальный локальный файл можно проверить без записи в production; при интеграционной проверке использовать отдельную тестовую БД/аккаунт. Существующие 27 карт в живом аккаунте не переимпортировать.

UI/онбординг:

- Новый пользователь видит предложение импорта, может пропустить, и подсказка объясняет путь в настройках. Пропуск переживает обновление и не закрывает остальной онбординг.
- Оба варианта размещения и пояснения видимы; слово «клиент» отсутствует в новом интерфейсе всех локалей; «Теги (метки)» и человеческая UTC-подсказка присутствуют.
- Названия/заметки из файла с HTML выводятся безопасным текстом. Ошибки видимы без различения цвета.
- Пустой файл, все строки ошибочны, все уже импортированы, частичный успех, пауза, истёкший preview и network retry проверены отдельно.
- Результат открывает нужные карты/профиль; неизвестный результат запроса не отображается как доказанный провал.

Добавить целевые тесты в `app/tests/test_chart_import_parsers.py`, `test_chart_import_api.py`, `test_chart_import_service.py`, `test_frontend_chart_import.test.cjs`; расширить `test_frontend_onboarding.test.cjs`, `test_preferences_onboarding.py` и проверки settings по фактическим изменениям.

После этапов выполнить все обязательные команды актуального `AGENTS.md`: `make all`, `make test`, `npm --prefix app run build:frontend`, четыре i18n-checker, перечисленные там Node suites, scoped flake8/mypy, полный pytest (`python3 -m pytest -q app/tests` в окружении проекта). Дополнительно явно запустить новые Node suites — текущие команды AGENTS перечисляют файлы и могут не подобрать их автоматически. Generated bundles обновлять сборкой, не вручную. Если проверка невозможна, указать причину и не объявлять её пройденной.

Пользователь ранее явно отказался от передачи кода внешнему `codex review` и выбрал локальное ручное ревью. Сохранить этот выбор: провести ручную проверку diff, прав доступа, транзакций, времён и UX; не запускать внешний review и не спрашивать это разрешение снова.

**11. Выпуск после реализации**

Подготовить последовательность: миграция → backend при выключенном флаге → frontend → smoke в тестовом аккаунте → включение флага. При проблемах отключение флага запрещает новые импорты, сохраняя уже созданные карты и receipts. Не удалять пользовательские данные для отката функции. Отдельно подтвердить состояние миграции и продемонстрировать импорт/повтор/возобновление до выпуска.
